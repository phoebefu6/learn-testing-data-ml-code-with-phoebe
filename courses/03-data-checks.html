Data checks that read the real rows

A unit test reads your code on five rows you wrote by hand. A data check reads every row of every batch the pipeline actually produced, so it sees bugs no fixture exercised and bugs that are not in your code at all. Tonight we write the static checks that guard the shape of each batch, see one idea written in three tools, and price the distribution checks that compare today with a known-good week, false alarms included.

Part 1 · covers schema, range, uniqueness, reconciliation, referential and split checks

Static checks: the shape of every batch

5 min live

A static check states a rule that holds for every batch, forever, with no reference to last week: a station id is three digits, a trip key appears once, a distance is either missing or between zero and fifty kilometres. It needs no history and no threshold to tune, so it is the cheapest kind of data check to trust. The figure shows Wrenfold's cleaned-trips table (Constructed Wrenfold example) and exactly which columns each check reads.

LiveFive static checks in Wrenfold's terms3 min▶

Each rule below is the exact rule the session 4 bench runs on Wrenfold's cleaned trips (Constructed Wrenfold example). Costs are modelled bench units, not timings.

CheckThe ruleUnits
SchemaDeparture and return station ids match ^\d{3}$, capacity is an integer, km is a float or missing2
Rangekm is missing or above 0 and at most 50; duration is at least 60 seconds; hour bucket is 0 to 743 (31 days of 24 hours)2
UniqueNo two clean rows share the trip key: seconds, duration, metres, departure station, return station3
ReferentialAt most 0.2% of kept trips point at a return station missing from the station table, and every forecast station is in it3
ReconcileClean rows equal the distinct raw rows that pass the rules; the aggregate total equals the clean rows it should count3

Notice what each rule refuses to assume. The range rule allows a missing distance on purpose: HSL records a distance of 0 or over 50,000 metres for some trips, and Wrenfold's cleaner turns those into null, never into 0.0. A range rule that read "km at least 0" would pass the silent null coercion bug, which writes exactly 0.0. The bound has to exclude zero for the check to catch it.

LiveReconciliation, the most productive check on the bench2 min▶

On the session 4 bench, reconcile fails on five of the twelve bugs for 3 modelled units: join fan-out, duplicated trips, dropped station, label shift and type coercion. No other single check catches more. It works because almost every quiet bug changes a count somewhere: fan-out adds rows, a skipped dedup doubles them, a dropped station loses departures between clean and aggregate, counting arrivals instead of departures moves the aggregate total.

The one condition that makes it work: the counting code must be independent of the pipeline's code. If your recount calls the pipeline's own clean() and compares the result with the pipeline's output, it compares a function with itself and agrees with every bug. Wrenfold's reconcile reads the raw file again, keeps station ids as the text the source wrote, drops exact duplicates and short trips with its own few lines of pandas, and only then compares counts. Under the type coercion bug the pipeline turns "030" into "30", rejects 8,395 trips as unknown and writes 5,071 rows; the independent recount still expects 13,465, and the check fails.

Self-studyThe one-unit check that is the only catch for leakage2 min▶

Wrenfold fits on 1 to 21 May and is scored on 22 to 31 May. The split check reads one thing: the days the fit actually used. If any is after day 21, it fails. It costs 1 modelled unit, the cheapest test on the bench.

On the bench it is the only test of all seventeen that fails on target leakage. Leakage moves the holdout error from 1.9113 to 1.7409, better, so a metric threshold passes it; it leaves rows, schema, ranges and distributions untouched, so every other data check passes it too. That is why the split check is one of the six tests in the cheapest set that catches all twelve bugs, which session 4 finds by exhaustive search. A check that reads the right thing is worth more than any amount of checking the wrong thing.

Real world

Every row twice, and three stations nobody listed. We downloaded HSL's May 2021 city bike file (CC BY 4.0) and counted it: 814,676 data lines, 407,338 distinct rows, every trip exactly twice. Of the 432 station ids the trips mention, three, 754, 997 and 999, are missing from HSL's 457-row station table. Both facts are invisible to a unit test of your code and obvious to a uniqueness check and a referential check on day one. That is why Wrenfold's cleaner deduplicates and why its referential rule allows up to 0.2% unknown return stations rather than zero: on the clean run, exactly one trip in the sample is rejected.

Part 2 · covers GX Core 1.x expectations and suites, pandera schemas, dbt data tests as a category

Three tools, one idea

5 min live

Great Expectations, pandera and dbt look different on the page and do the same thing underneath: you name a rule about the data, the tool finds the rows that break it, and the check fails if there are any. Pick the one that sits where your data already is. Below, two of Wrenfold's rules (Constructed Wrenfold example) are written in all three: km is missing or in (0, 50], and a station id is three digits.

LiveGX Core 1.x: expectations and suites2 min▶

Great Expectations defines the unit plainly: "An Expectation is a verifiable assertion about your data." In GX Core 1.x you create one as a Python class under gx.expectations, and an Expectation Suite groups the expectations that describe the same set of data: gx.ExpectationSuite(name=...), then suite.add_expectation(...).

Wrenfold's checks map onto standard 1.x classes: ExpectColumnValuesToBeBetween for the km and hour ranges, ExpectColumnValuesToNotBeNull for the station ids, ExpectColumnValuesToBeUnique for a single-column key, and ExpectColumnMedianToBeBetween for Part 3's median check. Two honest caveats. Wrenfold's trip key has five columns, and a single-column uniqueness expectation does not cover it: build one key column first, or look up a compound-key expectation in the gallery for your GX version. And every tool has its own convention for whether a bound is inclusive and how it treats nulls inside a range: read the docs for your version, then write a test row with km exactly 0.0 and confirm the check fails on it.

Say "GX Core 1.x" when you write about it. The 0.18 documentation is marked no longer actively maintained, and the 0.x API is different enough that a 0.x tutorial will mislead you.

Livepandera: a schema object for a DataFrame2 min▶

pandera keeps the checks next to your pandas code. Import it as import pandera.pandas as pa (the path introduced in v0.24.0), then describe the frame: pa.DataFrameSchema({"col": pa.Column(int, pa.Check.ge(0))}). Built-in checks such as pa.Check.ge and pa.Check.isin cover most rules; for anything else, pandera documents custom checks written as a function of the column, which is how the three-digit id rule is written in the figure.

By default schema.validate(df) stops at the first failure. With lazy=True it collects every failure into one pa.errors.SchemaErrors, which is what you want on a batch: one run, the whole list. Error messages read like "non-nullable series 'id' contains null values", specific enough to act on. If you prefer classes, pandera also offers a class-based form, a DataFrameModel whose fields carry constraints such as pa.Field(ge=0).

Self-studydbt data tests, as one category2 min▶

If your cleaned trips live in a warehouse and are built by dbt, the same checks belong there. A dbt data test is a select statement that returns the failing rows: zero rows means pass. A singular test is one SQL file, like the two in the figure. A generic test is reusable and configured on a column; dbt ships four: unique, not_null, accepted_values and relationships. Three of Wrenfold's checks map straight across: unique for the key (once it is one column), not_null for the ids, relationships for the referential rule.

Notice one convenience of SQL in the figure: where km <= 0 or km > 50 never selects a null km, because a comparison with null is not true. Missing distances pass, exactly as Wrenfold's rule wants. The craft of dbt tests inside a dbt project belongs to Learn Analytics Engineering, session a3.

Real world

dbt renamed its tests. dbt's documentation now says it plainly: "Tests are now called data tests to disambiguate from unit tests." The YAML key is data_tests:, with the old tests: still accepted as an alias. The rename is the distinction of the last two sessions, written into a tool: a unit test reads code on rows you wrote, a data test reads the rows your pipeline produced. Both are needed, and they catch different bugs.

Part 3 · covers static vs distribution checks and their false-alarm cost

Distribution checks and the false-alarm bill

5 min live

A static check asks "is this row legal?". A distribution check asks "does this batch look like a batch we trusted?". It catches bugs that keep every row legal: a km/miles slip leaves every distance in range and shrinks them all by the same factor. The price is a threshold, and a threshold can fire on a perfectly good batch. The figure shows Wrenfold's median-km check (Constructed Wrenfold example) under two thresholds.

LiveA stored profile from a known-good week2 min▶

A distribution check needs something to compare with. Wrenfold stores a profile from week 1 of a run it trusts (Constructed Wrenfold example): the median trip, 1.982 km, and the share of departures in each hour of the day, which peaks at 17:00 in that week. Each new batch is compared with that stored profile, never with itself.

Two checks read it. Median-km drift fails if the batch median moves more than a set fraction from 1.982. Hour-profile drift measures the total variation distance between the batch's 24 hour shares and the stored ones: half the sum of the absolute differences, 0 for identical profiles, 1 for profiles with nothing in common. On the clean May run the median is 2.0095 km, 1.4% above week 1, and the hour-profile distance is 0.0415. Even the peak moves: the whole month peaks at 16:00, with 10.3% of departures. A good batch is never identical to the profile, which is exactly why the threshold matters.

LiveChoose the threshold from the known-good value, not from fear2 min▶

Wrenfold's normal thresholds are a median within 15% of the profile and an hour-profile distance of at most 0.08. The clean month passes both, with room. The bugs these checks exist for land far outside: the km/miles bug moves the median to 1.2486, 37% below; the timezone bug moves the hour-profile distance to 0.2795, the off-by-one hour bug to 0.1062.

Now tighten them to 1% and 0.02, as a nervous team might after an incident. On the bench, with all 17 tests at tight thresholds, the clean pipeline raises 3 false alarms: median-km drift, hour-profile drift and the holdout metric. The bug count does not go up: 12 caught either way. Tight thresholds bought noise, not coverage. A check that fires on good data teaches the team to ignore it, and then it is worse than no check.

Where the line should sit is genuinely contested. One side: a loose band lets slow real drift through. The other: a tight band fires on normal variation and burns trust. The bench shows the cost of each on one pipeline; no rule of thumb we found settles it in general. Treat the threshold as a business choice you write down, not a statistical fact: measure how far good batches move, set the band outside that, and confirm the bug you fear lands outside the band.

Self-studyDrift after deploy is monitoring1 min▶

Tonight's distribution checks gate a batch before it ships: they run once, on the rows a commit or a nightly run produced, and a failure stops the release. Watching the same statistics on live traffic over weeks, with alerting and someone on call, is monitoring, and it has its own methods and its own false-alarm economics. Read Learn Data Observability, session b5 for drift detection and Learn ML Production, session 5 for choosing what to monitor at all.

Real world

A column that quietly went from 90% to 60%. Rule 10 of Zinkevich's Rules of Machine Learning is "Watch for silent failures". Its examples: Google Play once had a table that was stale for six months, and refreshing it alone gave a 2% boost in install rate; and a feature column populated in 90% of examples can suddenly drop to 60%. Neither crashes anything. Both are what a distribution check on a stored profile exists to notice: the share of non-null values in a column, compared with the share in a batch you trusted.

Build-along

A check suite for Wrenfold's cleaned trips

★ 22 min · everyone builds

You write the eight checks as Python, in the boxes below, in the order they will run (Constructed Wrenfold example). Read each one, edit it to taste, and write down what you expect it to fail on. Nothing runs here: running it on your own machine is Self-study, and on your own pipeline your numbers will differ. Session 4 runs exactly these rules against all twelve bugs on the real HSL trips.

Write the schema and range rules as one pandera schema. Schema and range are separate checks on the bench (2 units each), but in pandera they sit naturally in one object, so the comments mark which line is which. Notice the km rule: missing is allowed, 0.0 is not.

★ Step 1 · a pandera schema for cleaned tripsimport pandera.pandas as pa ID = r"^\d{3}$" # station ids are three-digit text: "030", not 30 trips_schema = pa.DataFrameSchema({ # schema: types and id pattern "s": pa.Column(str, pa.Check(lambda x: x.str.match(ID))), "r": pa.Column(str, pa.Check(lambda x: x.str.match(ID))), "cap": pa.Column(int), # schema + range: km is a float, missing allowed, else in (0, 50] "km": pa.Column(float, pa.Check(lambda x: (x > 0) & (x <= 50)), nullable=True), # range: the cleaner's own rules, checked on its output "dur": pa.Column(int, pa.Check.ge(60)), "hour": pa.Column(int, pa.Check.isin(list(range(744)))), # 31 days x 24 hours }) trips_schema.validate(clean_df, lazy=True) # raises pa.errors.SchemaErrors with every failure

Write the reconciliation in plain pandas, with its own counting. It must not import a single function from the pipeline. It re-reads the raw file with ids as text, deduplicates and applies the 60-second rule with its own lines, and only then compares. If you catch yourself calling clean() here, stop: you are comparing the pipeline with itself.

★ Step 2 · reconcile raw, clean and aggregateimport pandas as pd FORECAST = ["030", "126", "113", "041", "021"] def check_reconcile(raw_path, stations_path, clean_df, agg_total): # independent recount: read everything as text, never reuse pipeline code raw = pd.read_csv(raw_path, dtype=str) stations = pd.read_csv(stations_path, dtype=str) distinct = raw.drop_duplicates() long_enough = distinct[pd.to_numeric(distinct["dur"]) >= 60] known = long_enough[long_enough["r"].isin(set(stations["id"]))] expected_clean = len(known) assert len(clean_df) == expected_clean, ( f"clean has {len(clean_df)} rows, the raw file says {expected_clean}") # the aggregate must count exactly the clean departures it is meant to count in_scope = clean_df["s"].isin(FORECAST) & clean_df["hour"].between(0, 743) expected_agg = int(in_scope.sum()) assert agg_total == expected_agg, ( f"aggregate total {agg_total}, expected {expected_agg} departures")

Add uniqueness and the referential rule. Uniqueness reads the five-column key. Referential reads two numbers the cleaner already reports, kept and rejected, plus the station table. The 0.2% allowance is there because the real HSL file has return stations that are not in the table.

★ Step 3 · unique and referentialKEY = ["sec", "dur", "dm", "s", "r"] def check_unique(clean_df): dupes = int(clean_df.duplicated(subset=KEY).sum()) assert dupes == 0, f"{dupes} rows repeat a trip key" def check_referential(kept, rejected, stations, max_rate=0.002): rate = rejected / kept assert rate <= max_rate, f"{rate:.2%} of trips point at an unknown station" missing = set(FORECAST) - set(stations["id"]) assert not missing, f"forecast stations missing from the table: {missing}"

Add the two distribution checks against a stored profile. The profile is a dict you save from week 1 of a run you trust; the thresholds are the normal ones. Write the threshold next to the profile, where a reviewer will see it.

★ Step 4 · median-km drift and hour-profile driftPROFILE = { # stored from week 1 of a known-good run "median_km": 1.982, "hour_share": [...], # 24 shares of departures by hour of day, saved with it } THRESHOLDS = {"median_rel": 0.15, "hour_tvd": 0.08} # normal, chosen from good batches def check_median_km(clean_df): med = clean_df["km"].median() # pandas skips missing km change = abs(med / PROFILE["median_km"] - 1) assert change <= THRESHOLDS["median_rel"], ( f"median {med:.4f} km is {change:.1%} away from the profile") def check_hour_profile(clean_df): share = (clean_df["hour"] % 24).value_counts(normalize=True) share = share.reindex(range(24), fill_value=0.0) tvd = 0.5 * (share - pd.Series(PROFILE["hour_share"])).abs().sum() assert tvd <= THRESHOLDS["hour_tvd"], f"hour profile moved {tvd:.4f} from week 1"

Add the split check. One line of logic, 1 modelled unit, and the only check on the bench that fails on target leakage.

Homework

Before session 4

30 min
  1. Finish Wrenfold's suite on paper. For each of the eight checks, write the one bug from the inventory you expect it to fail on first, and the bug you expect it to miss that you most wish it caught.
  2. Write a reconciliation for one table you own. Raw count, clean count, aggregate total, each computed by code that shares nothing with the pipeline. Note where your two counts disagree today, and why.
  3. Store one profile. Pick one column in a batch you trust, save its median (or its null share) and look at how far the last four good batches moved from it. Set a threshold outside that movement and write the reason next to it.
  4. Find a check that has never failed. In a suite you run, pick one data check and build a batch that should break it. If it stays green, you have found a check that reads the wrong thing.
Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · A teammate writes Wrenfold's reconciliation by calling the pipeline's own clean() on the raw file and comparing its row count with the pipeline's output. Why will this check miss the type coercion bug?

A check that reuses the code under test agrees with every bug in it. Wrenfold's reconcile re-reads ids as text with its own lines, so it still expects 13,465 rows while the buggy pipeline writes 5,071.

2 · The stored week-1 median trip is 1.982 km. The clean May run has a median of 2.0095 km. Why does a plus or minus 1% band raise an alarm on that clean month?

The 15% band runs from about 1.685 to 2.279 km, so the clean month passes it and the km/miles bug at 1.2486 still fails it. On the bench, tight thresholds add 3 false alarms and catch no extra bug.

3 · With the stale reference table bug, 65 trips are rejected (0.48%) and the forecast error is 1.9062. At normal thresholds, which of the seventeen tests on the bench fails?

The error 1.9062 is under the 2.2 bar, the reconcile recount uses the same station table the pipeline joined, and distributions barely move. Only a check that reads the reference table itself notices that it is missing stations.
