Unit tests for transforms

A unit test calls one function on a few rows you wrote by hand and checks the answer. That sounds too small to matter for a pipeline that eats a whole month of trips, until you notice that seven of the twelve quiet bugs from session 1 live inside four small functions. Tonight we write those four tests with pytest, fixtures, parametrize and three fake distances, pull the logic away from the files so testing it stays cheap, and say plainly which five bugs no unit test will ever see.

Part 1 · covers pytest test anatomy

Arrange, act, assert on three fake trips

5 min live

Every useful unit test has the same three moves. Arrange the inputs, act by calling the one function under test, assert on what came back. The craft is almost entirely in the first move: which rows do you write? For Wrenfold's distance cleaner (Constructed Wrenfold example), three hand-written distances are enough to fail on two of the twelve bugs, because each one takes a different path through the code.

LiveArrange, act, assert3 min▶

pytest's own documentation labels the steps of its examples with exactly these comments, and the habit is worth copying even in a three-line test. It forces you to say what the inputs are before you say what you expect.

★ The shape of every unit test (Constructed Wrenfold example)def test_distance(): # Arrange: one ordinary trip, one zero, one over 50 km metres = [2043, 0, 60000] # Act: call the one function under test out = [dist_km(m) for m in metres] # Assert: compare with the answer you worked out by hand assert out == [2.043, None, None]

Arrange is where the thinking happens. 2043 m is a normal trip: it proves the division is by 1000. 0 m and 60000 m are the two ways Wrenfold's cleaner treats a distance as missing: zero, and over 50,000 m. Leave either out and the test still passes on correct code, but it can no longer fail on the null coercion bug, because no fake row ever walks down that path.

Assert on the exact answer you worked out by hand. Not "is a float", not "is positive". A loose assert lets 1.269 through as happily as 2.043.

LiveWhat a unit test can see: only the function it calls, on the rows you wrote2 min▶

A unit test's field of view is two things wide: the code inside the function it calls, and the rows you handed it. Inside that field it is precise, fast and cheap: the bench prices each unit test at 1 modelled unit, the lowest of any test type. Outside it, a unit test is blind.

That blindness is not a flaw to fix with bigger fixtures. It is the definition. The HSL file with every row twice, a station table that is six months out of date, a model fitted on the days it is scored on: none of these is a wrong line inside dist_km, so no fake row passed to dist_km can reveal them. Those bugs belong to the data checks of session 3. Keep the two jobs separate and each test stays small enough to read.

Real world

Test the plumbing apart from the learning. Rule #5 of Martin Zinkevich's Rules of Machine Learning is "Test the infrastructure independently from the machine learning." It sits next to Rule #4, "Keep the first model simple and get the infrastructure right." Unit tests on transforms are the cheapest way to follow it: a distance cleaner or an hour bucketer has a right answer you can work out on paper, with no model in sight.

Part 2 · covers fixtures, scopes, yield teardown, parametrize, pytest.param marks

Fixtures and parametrize

6 min live

Two pytest features carry most of the weight in data tests. A fixture hands the same small set of rows to every test that asks for it, so the rows are written once and named. Parametrize turns one test function into many cases, so the edge values you care about each get their own line in the report. Wrenfold's bucketing and aggregation tests use one each (Constructed Wrenfold example).

LiveFixtures: rows a test asks for by name3 min▶

A test requests a fixture by declaring it as an argument. pytest matches the parameter name to a fixture function of the same name, runs it, and passes in what it returns. No import, no call: the name is the wiring.

★ A fixture and the test that asks for it (Constructed Wrenfold example)import pytest @pytest.fixture def one_trip(): return [{"s": "001", "r": "002", "hour": 5}] def test_aggregate(one_trip): agg = aggregate(one_trip, ["001", "002"]) assert agg["001"][5] == 1

Scope says how often the fixture runs: function (the default, a fresh one for every test), class, module, package or session. Keep small row lists at function scope so no test can change the rows another test sees. Widen the scope only for something expensive and read-only.

Teardown with yield. pytest recommends yield fixtures for clean-up: everything before the yield is setup, everything after it runs once the test finishes, and teardowns run in the reverse order of their setups. A temporary table, a connection, a file you created: build it, yield it, remove it.

LiveParametrize: one function, many cases3 min▶

@pytest.mark.parametrize("test_input,expected", [...]) runs the test once per tuple in the list. Four tuples, four test cases, each passing or failing on its own line. That matters for edge values: if the off-by-one bug breaks 3599 s and nothing else, the report says so directly instead of "test_bucket failed".

★ The four hour-bucket cases, and one marked case@pytest.mark.parametrize("sec,expected", [ (0, 0), (3599, 0), (3600, 1), (2678245, 743), pytest.param(-1, 0, marks=pytest.mark.xfail), ]) def test_bucket(sec, expected): assert hour_bucket(sec) == expected

pytest.param(..., marks=pytest.mark.xfail) marks one case without touching the others. The -1 second case here is our illustration: a trip logged before 1 May has no defined bucket, and the case records that we know it, rather than hiding it. Use the mark for a known open question, never to silence a case that started failing.

Self-studyProperty-based tests with Hypothesis4 min▶

Hypothesis calls itself "the property-based testing library for Python". Instead of listing cases, you state a property that should hold for every input in a described range, and Hypothesis chooses the inputs. @given turns a function into a Hypothesis test; strategies such as integers() describe what to generate. When it finds an input that breaks the property, it reports a counterexample, and its strategies document how they shrink a failing example towards a simpler one before reporting it.

★ A bucketing property (our example, not from the Hypothesis docs)from hypothesis import given, strategies as st # every second of May, 0 to 31 x 86400 - 1 @given(st.integers(min_value=0, max_value=2678399)) def test_bucket_contains_its_second(s): b = hour_bucket(s) assert b * 3600 <= s < (b + 1) * 3600

The property is "the hour a second lands in actually contains that second". The four parametrized cases check four points; the property checks the rule. The ceiling bug breaks it for every second that is not exactly on an hour: at s = 1 the bucket is 1, and 1 x 3600 is not at or below 1. The timezone bug breaks it everywhere, because the bucket is three hours ahead of the second. Neither of those outcomes is something we ran; work them through on paper and then run it locally.

Hypothesis also has a separate section of strategies for pandas objects. We name it and stop there: read its own documentation before you rely on it.

Real world

dbt renamed its tests so nobody would confuse the two kinds. dbt's checks are select statements that return failing rows over real tables. Its documentation now says "Tests are now called data tests to disambiguate from unit tests", and keeps tests: as an alias of data_tests:. The rename draws the same line as this session: a unit test reads code on rows you wrote; a data test reads the rows that actually arrived. Session 3 is about the second kind.

Part 3 · covers testing pure functions vs IO

Pure functions are cheap, IO is dear

4 min live

A function that only takes values and returns values is a pure function, and testing it costs one line of fake data. A function that opens a file, reads the clock or queries a warehouse drags all of that into every test. The fix is a shape, not a tool: keep the reading and writing at the thin edges and push every rule into the pure middle. Here is Wrenfold's cleaner before and after (Constructed Wrenfold example).

LiveSeparate IO from logic2 min▶

Look at what Wrenfold's cleaner actually decides: which rows are duplicates, which trips are under 60 seconds, what a distance is in km, which hour a trip belongs to, which return stations are unknown. None of those decisions needs a file. They need values. Pull them into clean(rows) and every one of them becomes a three-row unit test.

★ The split, in outline (Constructed Wrenfold example)def read_trips(path): # IO: parse the CSV, nothing else ... def clean(rows, stations): # pure: every rule lives here ... def write_trips(rows, path): # IO: write the CSV, nothing else ... def run(in_path, out_path, stations): write_trips(clean(read_trips(in_path), stations), out_path)

The test for "a trip under 60 seconds is dropped" is now a list with one 59-second trip in it. Before the split, the same test needed a CSV fixture, a temporary output path and a parser to read the result back, and it would break whenever the file format changed, which has nothing to do with the rule it was meant to check.

Self-studyOne integration test for the edges3 min▶

The thin edges still need a test, but only one, and it checks plumbing, not rules: that a file written by write_trips comes back unchanged through read_trips, and that run wires the three together. pytest ships a built-in tmp_path fixture that gives each test its own temporary directory, so the test never writes into your project.

★ One edge test with tmp_path (Constructed Wrenfold example)def test_round_trip(tmp_path): rows = [{"sec": 26400, "dur": 600, "dm": 2043, "s": "030", "r": "126"}] path = tmp_path / "trips.csv" write_trips(rows, path) assert read_trips(path) == rows

Notice the station ids are strings with their leading zero. That is deliberate: a reader that turns "030" into 30 is the type coercion bug from session 1, and the round trip is the one unit-level place where the file's own parsing is in view. Even so, it only checks the row you wrote. Whether the real May file reads cleanly is a question for the data checks in session 3.

Real world

The rubric asks for both kinds. The ML Test Score by Breck and colleagues at Google (IEEE Big Data 2017) has a section of tests for ML infrastructure. Unit testing of the model specification code sits on that list, and so does "The ML pipeline is integration tested". The paper gives each test the same weight: half a point if it is run by hand with the results written up and shared, a full point if it runs automatically on a repeated basis. Pure-middle unit tests and one edge test are the cheapest way to earn both points, and to earn them automatically.

Build-along

Four tests for Wrenfold's trip cleaner

★ 22 min · everyone builds

You will write the four unit tests the session 4 bench calls u_distance, u_bucket, u_aggregate and u_parity (Constructed Wrenfold example; the functions are the Python form of the pipeline that runs on real HSL May 2021 trips, but the tests use only rows you write). Read each function, write its test in the box, and say out loud which bug from the inventory it would fail on. Running them locally is Self-study; everything below can be done by reading and editing.

Read the functions under test. These are the Python form of Wrenfold's cleaner, bucketing, aggregation and feature code, simplified to the correct path with no bug switches (Constructed Wrenfold example). Every rule here is one the bench engine implements: a distance of 0 or over 50,000 m is missing, never 0; the hour is a floor of seconds since 1 May 00:00 local; aggregation counts departures per station; training and serving build the hour feature with the same function.

★ Step 1 · the functions under testWEEKEND = {1, 2, 8, 9, 15, 16, 22, 23, 29, 30} # May 2021 weekend days HOURS = 744 # 31 days x 24 def dist_km(m): if m == 0 or m > 50000: return None # missing, never 0.0 return m / 1000 def hour_bucket(sec): return sec // 3600 # floor: 07:20 belongs to hour 7 def aggregate(rows, stations): agg = {s: [0] * HOURS for s in stations} for row in rows: h = row["hour"] if 0 <= h < HOURS and row["s"] in agg: agg[row["s"]][h] += 1 # count at the departure station return agg def train_feat(h): day = h // 24 + 1 return (1 if day in WEEKEND else 0, h % 24) def serve_feat(h): return train_feat(h) # one code path for both

Write test_distance. Three fake distances, one per path through dist_km. The bench's u_distance is exactly this assert. It fails on the km / miles bug (the first value becomes 1.269...) and on the null coercion bug (the two missing values become 0.0).

★ Step 2 · test_distance, three fake distancesdef test_distance(): # Arrange: an ordinary trip, a zero, one over 50 km metres = [2043, 0, 60000] # Act out = [dist_km(m) for m in metres] # Assert assert out == [2.043, None, None]

Write test_bucket with parametrize. Four seconds: the very start of May, one second before the first hour edge, exactly on it, and 31 May 23:57:25. The off-by-one bug (ceiling where it needed floor) fails case 2: 3599 s becomes hour 1. The timezone bug adds three hours to every second, so case 1 already fails: 0 s becomes hour 3.

★ Step 3 · test_bucket, four parametrized casesimport pytest @pytest.mark.parametrize("sec,expected", [ (0, 0), # 1 May 00:00:00 (3599, 0), # one second before the edge (3600, 1), # exactly on the edge (2678245, 743), # 31 May 23:57:25, the last hour of May ]) def test_bucket(sec, expected): assert hour_bucket(sec) == expected

Write test_aggregate with a fixture. One trip from station "001" to "002" at hour 5. Three asserts: both station keys exist, "001" counts the trip, "002" does not. Each assert is there for a bug. The dropped-station bug stops the loop one station early, so "002" is missing. The label-shift bug counts arrivals, so "001" reads 0 and "002" reads 1.

★ Step 4 · test_aggregate, one trip in a fixture@pytest.fixture def one_trip(): return [{"s": "001", "r": "002", "hour": 5}] def test_aggregate(one_trip): agg = aggregate(one_trip, ["001", "002"]) assert "001" in agg and "002" in agg # no station dropped assert agg["001"][5] == 1 # counted at departure assert agg["002"][5] == 0 # not at arrival

Write test_parity. The training and serving paths must build the same feature for the same hour. Five hours spread across the month, weekday and weekend, early and late. The serve-skew bug computes the serving hour three hours off, so every case fails. The bench runs these five hours as one test; parametrizing them gives five lines in your report instead.

★ Step 5 · test_parity, five hours@pytest.mark.parametrize("h", [0, 7, 100, 503, 600]) def test_parity(h): assert train_feat(h) == serve_feat(h)

Predict before you look. Go down the bug inventory from session 1 and mark each row "caught" or "ships" for these four tests alone. Then check against the figure above. Session 4 runs the same four on the bench: 7 caught, 5 ship, 4 modelled cost units. If you marked duplicated trips as caught, ask which fake row in steps 2 to 5 could ever have a twin.

Write the bug next to the test. A test whose docstring names the bug it would fail on is a test the next person can judge, keep or delete. "Fails on null coercion and km / miles" says more than any test name.

Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · test_distance feeds dist_km three values: 2043 m, 0 m and 60000 m. Why are 0 m and 60000 m in the fixture at all?

A unit test can only fail on a bug its rows exercise. 2043 m catches the unit bug; the two missing values are what make the null-to-0.0 bug visible.

2 · What does @pytest.mark.parametrize("sec,expected", [...]) with four tuples do to test_bucket?

Parametrize expands one function into one case per tuple. Generating inputs from a described range is what Hypothesis does, and that is a different tool.

3 · The HSL May 2021 file carries every trip twice. Why can none of the four unit tests see it, even with bigger fixtures?

On the bench, duplicated trips is caught by d_reconcile, d_unique, b_inv and m_holdout, and by no unit test. It is one of the five that ship from the unit rung.
