What test would fail if the code were wrong?

A web service that breaks throws an error and someone gets paged. A data pipeline that breaks usually does neither: the job finishes, the table refreshes, the dashboard looks normal, and a number in it is wrong. Tonight we name the twelve ways a data and ML pipeline goes wrong quietly, redraw the test pyramid for code, data and model, and break a real pipeline in the page while its only test stays green.

Part 1 · covers silent failure

The job succeeded. The number is wrong.

5 min live

Most software tests were designed for code that fails loudly: a wrong type throws, a missing key crashes, a bad request returns an error. Data code fails in a different shape. A wrong value is still a valid float, a duplicated row is still a valid row, a shifted hour is still an hour between 0 and 23. The pipeline has no reason to stop, so the only check most teams start with, "did the job run and write rows?", stays green.

LiveLoud failures and quiet ones3 min▶

Loud. The input file is missing, a column is renamed and the code throws KeyError, the warehouse is down. The job goes red, an alert fires, somebody fixes it. Annoying, but the wrong number never reaches a reader.

Quiet. A distance is read in metres and divided as if it were miles. A join adds a second row for two stations. A timestamp written in local time is parsed as UTC. Each of these produces rows of the right type, in the right columns, in roughly the right quantity. Nothing throws. The forecast still forecasts. It is just forecasting the wrong thing, and the first person to notice is usually a user who knows what the answer should look like.

The working rule for the rest of the sessions follows from that: for every quiet bug you can name, ask which test would fail. If the honest answer is "none of the ones we run", the bug ships.

Self-studyWhy a green suite can still lie (one-card recap)2 min▶

The general argument, that a passing suite proves only that the tests you wrote pass, and that a test is worth what it would catch, is taught properly in Learn AI QA, session 1 and session 2. Read those for software in general. What is different here is where the lie comes from: in application code it is usually a missing test; in data code it is often a test that reads the wrong thing, such as the exit code instead of the values.

Real world

A public file with every row in it twice. HSL publishes Helsinki's city bike trips as monthly CSV files under a CC BY 4.0 licence. The May 2021 file has 814,676 data lines and only 407,338 distinct rows: every trip appears exactly twice, one line after the other. We counted it while building the bench. A pipeline that loads it without a de-duplication step doubles every count it produces, runs without a single error, and keeps doing so every month.

Part 2 · covers the bug classes of data and ML code

Twelve ways the pipeline can be wrong

6 min live

The useful unit is not "a bug" but a bug class: a kind of mistake that recurs across teams, with a predictable place it enters and a predictable test that would notice it. Here are the twelve that Wrenfold's pipeline is built to suffer, placed at the stage where each one gets in. Every one of them is a real code-path change in the session 4 bench, not a description.

LiveThe three model bugs, and why the metric will not save you3 min▶

Target leakage fits the model on days it is later scored on. Label shift quietly changes what the target means: Wrenfold's forecast should count departures from a station, and the buggy aggregation counts arrivals. Train/serve skew computes a feature one way when training and another way when serving, here the hour of day in local time for training and in UTC for serving. Google's Rules of Machine Learning defines training-serving skew as "a difference between performance during training and performance during serving", and lists a different handling of data in the two pipelines as its first cause.

The tempting defence is the holdout metric: if the forecast gets worse, a threshold on its error will fail. On the bench, Wrenfold's clean forecast is off by 1.9113 trips per station-hour on 22-31 May. With target leakage it scores 1.7409. With label shift it scores 0.3277. Both bugs make the number better. A threshold that fails when error rises can never catch a bug that lowers it.

Self-studyWhy these twelve and not others2 min▶

The list is a working inventory for one pipeline, not a published taxonomy. Each class was kept because it meets three tests of its own: it produces valid-looking output, it recurs in real data work, and it can be planted as a one-line change in Wrenfold's code so the bench can show which test notices it. Your pipeline has its own list. Session 6 asks you to write it, and the habit transfers even where the classes do not.

Two classes worth adding for many teams are missing on purpose, because they need data this bench does not have: late-arriving rows (a batch that is complete today and not tomorrow) and feedback loops (the forecast changes where bikes are, which changes the trips the next forecast learns from). The Rules of Machine Learning names the second as the third cause of training-serving skew.

Real world

A stale table, six months, two percent. Rule 10 of Martin Zinkevich's Rules of Machine Learning is "Watch for silent failures". Its example: Google Play once had a table that was stale for six months, and refreshing that table alone gave a 2% boost in install rate. Nothing crashed in those six months. The system adjusted around the stale data and performance decayed slowly enough that nobody saw a cliff.

Part 3 · covers the test pyramid adapted for data

A pyramid with a middle layer for data

4 min live

The classic test pyramid has many cheap unit tests at the bottom and a few expensive end-to-end tests at the top. Data and ML code needs the same shape with one change: there are three different things that can be wrong, the code, the data that flows through it and the model fitted on that data, and each needs tests that read it directly.

LiveThree layers, three things they read2 min▶

Unit tests read the code. They call one transform on a handful of rows you wrote by hand and check the answer. They are fast, they run on every commit, and they catch a bug in the function they call, if a fixture exercises that path. Session 2.

Data checks read the data. They run on every real batch: are the columns and types right, do the counts reconcile from raw to clean, is the trip key unique, is every distance in range, does every station exist, has the distribution moved. They catch bugs in code that no unit test covers, and bugs that are not in your code at all, such as a source file with every row twice. Session 3.

Behaviour and metric tests read the model. They need a fitted model, so they are the dearest to run. They catch what only shows up in predictions: a forecast that is higher at 04:00 than at 08:00, a forecast that does not fall when a station closes. Session 5.

Self-studyCost per run is not cost per bug2 min▶

A pyramid tells you how many of each kind you can afford to run often. It does not tell you which ones are worth having. A one-unit test that catches three bugs is worth more than three one-unit tests that each catch the same one. Session 4 turns that into a measurement: for each bug, which tests fail; for each test, what it costs; and the cheapest set that leaves no bug shipping.

Real world

Thirty-six teams and twenty-eight tests. Breck and colleagues at Google published "The ML Test Score" in 2017: 28 tests and monitoring needs for production ML, in four sections, features and data, model development, infrastructure and monitoring. In a survey of several dozen teams at Google, none of the 28 was implemented by more than 80% of teams. These were not careless teams; the paper's point is that ML-specific tests are non-obvious even where testing is a strong habit. Session 5 scores Wrenfold on it.

Break a Wrenfold transform

The widget below runs Wrenfold's real pipeline on the real trips in your browser (Constructed Wrenfold example). Pick a bug, and it re-runs every stage with that one code path changed, then shows what moved and what Wrenfold's only existing test says about it. Nothing to install.

Read Wrenfold's existing test first. This is the whole suite Wrenfold runs today (Constructed Wrenfold example). Say out loud which of the twelve bugs it could ever fail on.

★ Step 1 · Wrenfold's test suite, as founddef test_pipeline_runs(tmp_path): out = run_pipeline(month="2021-05", out_dir=tmp_path) assert out.exit_code == 0 assert len(out.trips) > 0

Pick "Timezone shift" in the widget. Read the three lines that matter: the smoke test, the rows written, the forecast error. The rows written stay at 13,465. The forecast error goes from 1.9113 to 1.9098, essentially unchanged, because the model learned the shifted hours and is scored on shifted hours too. The hour profile distance jumps from 0.0415 to 0.2795. Only a test that reads the hours would notice.

★ Step 2 · what to write downBug: timezone shift Stage: clean (parse timestamps) Smoke test: green Rows: 13,465 -> 13,465 Forecast error: 1.9113 -> 1.9098 Hour profile: 0.0415 -> 0.2795 A test that would fail: one that checks a known timestamp lands in the right hour, or one that compares the hour profile with last week's.

Now pick "Duplicated trips", then "Target leakage". Duplicated trips doubles the rows to 26,930 and the error to 3.8226; that one a metric threshold would notice. Target leakage leaves the rows alone and improves the error to 1.7409. Write both down in the same shape as step 2.

Work through the other nine. For each, note what moved and your first guess at the cheapest test that would fail. Do not look up session 4 yet: the point is to see how good your instincts are before the bench measures them.

Mark the ones where the forecast error got better or stayed put. Those are the bugs a holdout threshold can never catch. Keep the list: session 2 writes the first unit tests against it and session 4 scores every guess on it.

Ask the question before you write the test. "What would this test fail on?" is cheaper to answer before the test exists than after. A test with no bug it would fail on is a cost with no catch, however green it looks.

Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · Wrenfold's only test asserts the job exits with code 0 and writes more than zero rows. With the timezone bug planted, the rows written stay at 13,465. Why does that test stay green?

The check and the bug never meet. A test catches a bug only if it reads the thing the bug changed; a smoke test reads that the job ran.

2 · On the bench, target leakage scores a forecast error of 1.7409 against the clean 1.9113. What does that tell you about a holdout threshold such as "error must stay at or under 2.2"?

Leakage flatters the metric by letting the model see the answers. The fix is a test of the split itself, which costs almost nothing; session 3 writes it.

3 · In the pyramid redrawn for data, what does the middle layer read that the bottom layer does not?

Unit tests read code on fake rows; data checks read the real data; behaviour tests read the model. The HSL file's doubled rows are a data fact no unit test of your code can see.
