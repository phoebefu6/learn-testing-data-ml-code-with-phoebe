Part 1 · covers what runs when

Per commit, nightly, at release

5 min live

A lane is a trigger plus the thing the tests in it can read. A commit gives you new code and nothing else, so its tests read code on rows you wrote by hand. A night gives you a new real batch, so its tests read the data. A retrained model gives you predictions, so its tests read the model. Put a test in a lane that cannot feed it what it reads, and it either cannot run or it runs on the wrong thing. Here are Wrenfold's three lanes on the bench (Constructed Wrenfold example).

LiveThree triggers, three things they read3 min▶

Per commit: the code. The smoke test and the four unit tests from session 2 need nothing but the function and a few rows you wrote, so they can run on every merge request and block it. On the bench they cost 5 units and catch 7 bugs. The five they miss are not in any function the fixtures call: the doubled source file, a history table the fixtures never contain, how the loader reads a column, a stale station table, which days the model is fitted on.

Nightly: the data. The eight data checks from session 3 need the real batch, so they run when the batch lands. They cost 24 units and catch 11. The one they miss is train/serve skew, and the reason is instructive: the skew is in the serving code's hour feature, and the data checks read cleaned trips, which the serving path never touches. The per-commit parity test catches it for 1 unit. Neither lane is enough alone; together they catch all twelve for 29 units, with no false alarm on the clean run.

At release: the model. The behaviour tests from session 5 and the holdout bar need a fitted model, so they run when one is retrained. They cost 50 units and catch 5, every one of which the two lanes above already catch on this bug list. Step 4 of the capstone asks whether that lane earns its cost anyway.

Self-studyWiring the lanes into CI3 min▶

Turning a lane into a job that actually fires (a workflow file, a scheduler entry, a gate on a release) is CI work, and it is taught properly in Learn DataOps, b1 (the repo and its pipeline) and Learn DataOps, b3 (data tests and contracts in that pipeline). Bring four things from tonight to that wiring: the lane's trigger, the tests in it, its budget, and the role that is paged when it goes red. If you cannot fill all four for a test, it is not ready to wire.

Real world

Half a point for doing it by hand. The ML Test Score (Breck, Cai, Nielsen, Salib and Sculley, IEEE Big Data 2017) gives a test half a point if it is run manually with the results documented and distributed, and a full point only if it runs automatically on a repeated basis. Points are summed per section and the final score is the minimum of the four sections. The authors say all tests are worth the same number of points on purpose, because the relative importance of tests varies by team. The rubric is scoring exactly tonight's subject: a test that waits for someone to remember it is worth half a test that a trigger runs.

Part 2 · covers runtime budget and redundancy

A runtime budget, and the thin rows

6 min live

Every lane has a budget: a merge request can only wait so long, a nightly job has to finish before people read the numbers, a release gate has to fit in the release. Spend it on catches, not on habit. Plot each of the seventeen tests by what it costs and what it catches on Wrenfold's twelve bugs (Constructed Wrenfold example), and the spending decisions mostly make themselves. Two rows of the catch matrix still need something the bench does not have.

LiveSpend the budget where the catches are2 min▶

Read the plot top left to bottom right. Row reconciliation, counting rows from raw to clean to aggregate, costs 3 modelled units and catches 5 of the twelve bugs: join fan-out, duplicated trips, dropped station, label shift and type coercion. The range checks catch 3 for 2 units. Three of the unit tests catch 2 each for 1 unit. At the other corner, the invariance test re-runs the whole pipeline for 20 units and catches one bug, duplicated trips, which reconciliation and the uniqueness check already catch.

That does not make INV worthless. It makes it a poor fit for a lane with a tight budget. A useful rule of thumb for any lane: sort the candidate tests by bugs caught per unit, fill the cheap lane from the top, and push what is left to a lane that runs less often. The numbers on this plot are modelled units, not seconds, so trust the ordering more than the ratios. And remember the counts overlap: d_reconcile's 5 and d_unique's 2 share two bugs, so together they catch 5, not 7.

LiveSingle points of failure: two bugs with one test each2 min▶

Turn on all seventeen tests and read the catch matrix row by row. Ten bugs are caught by two or more tests. Two are not: target leakage is caught only by d_split, and the stale reference table only by d_referential. There is no second line for either anywhere on the bench, so adding more of the tests you already have buys nothing for those two rows. If one of those checks is muted, misconfigured or deleted in a tidy-up, its bug ships and nothing else notices.

The second line has to be a new test you write, one that reads something different. Two ideas, offered as ideas and not measured on the bench:

  • Idea, for leakage: log the date range the model was actually fitted on, and compare it with the scored days. The split check reads the split you asked for; this reads the fit that happened.
  • Idea, for the stale table: a check that the station table's row count is not below last month's. The referential check reads trips against the table; this reads the table against its own history.
Self-studyRedundancy is insurance for the bug you have not named3 min▶

The cheapest full catch, six tests for 10 units, was found by an exhaustive search that knew all twelve bugs in advance. A real team does not know its next bug. Every test you drop because "another test already catches that" is a bet that the overlap you measured on known bugs holds for unknown ones. Sometimes it will: reconciliation catches anything that changes row counts, whatever its cause. Sometimes it will not: the split check catches exactly one way of fitting on the wrong days.

So write the redundancy choice down as a choice. Three honest positions: run the cheapest set and accept that each of its rows is one failure from shipping; run the cheapest set plus a second line for the rows you most fear; or run everything that fits the budget and accept the cost. The bench can price each option. It cannot tell you which bug comes next, and nothing published that we found measures how much redundancy pays off.

Real world

Six months stale, two percent back. Rule 10 of Martin Zinkevich's Rules of Machine Learning, "Watch for silent failures", tells of a table in Google Play that went stale for six months. Refreshing that table alone gave a 2% boost in install rate. That is Wrenfold's stale reference bug at production scale, and the lesson for a plan is the thin row: if one check stands between you and a stale table, the day that check is off is the first day of the six months.

Part 3 · covers flaky data tests and ownership

Flaky data tests and who owns a red check

4 min live

A data check that fails on normal data will be muted within weeks, and then it catches nothing. A check that fails on a real bug and has nobody assigned to it will be ignored, which is the same outcome more slowly. Both are strategy failures, not test failures. Here is what should happen between "the check went red" and "the check is green again", drawn for Wrenfold (Constructed Wrenfold example).

LiveA flaky data test is a threshold inside normal variation2 min▶

In application code a flaky test usually means timing, ordering or shared state. A data check is flaky for a simpler reason: its threshold sits inside the range that normal batches move through, so some nights it fails on nothing at all. On the bench, Wrenfold's clean month has a median trip of 2.0095 km against a stored 1.982, and an hour-profile distance of 0.0415. Both pass at the normal thresholds (within 15%, at most 0.08). Press "Tighten thresholds" (1%, 0.02, MAE at most 1.9) and the clean pipeline, with no bug in it, raises false alarms: 2 in the nightly lane (the two distribution checks) and 1 in the release lane (the holdout bar, since the clean MAE is 1.9113).

The bench runs one clean month, so it shows the false alarm as a fixed fact. A real nightly job sees a new batch every night, and a threshold set that close to normal fails on some nights and not others. That is what a flaky data test looks like from the outside. The cure is the order of work from session 3: measure the known-good value first, then put the bar outside normal variation and inside the drift you would act on. Where exactly is a business choice, not a statistical fact, and teams reasonably disagree.

LiveEvery check has an owner and a one-line runbook2 min▶

"The team owns it" means nobody does. Give each lane an owner role, the person who is paged and who decides which of the three ways out applies. In Wrenfold's constructed plan: the analytics engineer owns the per-commit lane (the transforms), the data engineer owns the nightly lane (the batch and its source), the ML engineer owns the release lane (the model).

Then give each check one line that answers "what do I look at first?". For example, for the nightly row reconciliation: "Counts disagree: compare raw and clean row counts; a ratio near 2 means duplicated source rows; a jump in clean rows after a join means fan-out." One line is enough for the owner at 07:00 to pick a path instead of a mute button.

Self-studyFlakes in general, and monitoring after deploy3 min▶

Flaky tests in general software, their causes, quarantine and the cost of a slow suite are taught in Learn AI QA, session 5. Everything tonight stops at "before it ships". Once the forecast is live, the questions change to which signals to watch and who acts on them: see Learn ML Production, session 5 and, for drift in the data itself, Learn Data Observability, b5. The nightly distribution checks here are the pre-ship cousin of that monitoring; the owner-and-runbook habit carries straight over.

Real world

From 90% to 60%, quietly. Rule 10 of the Rules of Machine Learning also warns that a feature column populated in 90% of examples can drop to 60% without anything failing. A not-null rate check would see it. Whether anyone acts depends on everything in this Part: a threshold set from the known-good value rather than a guess, so it is not already muted for crying wolf, and a named owner who reads the alert the morning it fires.

Press "+ behaviour tests" and decide whether the release lane earns its 50 units. All seventeen are on: still 12 caught, now 79 units. On this bug list the release lane adds no catch. Argue both sides before you decide. Against: on the bench it is 50 units of cost for nothing found, and Zinkevich's Rules 1 and 4 say keep a first model simple and get the infrastructure right before spending heavily on the model. For: it is the only lane that reads what the model predicts, so it is the only one that could see a bug living in the model's behaviour rather than in the code or the data, and Breck et al. found ML-specific tests under-implemented at every team they surveyed (none of the 28 above 80% of teams). Breck et al. also note that different systems may reasonably aim at different points on their scale. No study we found measures the payoff curve; write your choice and your reason.

Score the plan, not the tests. A strong test in the wrong lane, or with nobody to answer it, is worth less than a modest one that runs every night and has an owner. The bench scores which bugs a set of tests would catch; whether they are run, read and acted on is the part only the plan decides.

Homework

After the last session

30 min
  1. Write the plan for a pipeline you own. Three lanes with their triggers, the tests in each, a runtime budget per lane, and an owner role for each lane. Use your session 1 bug inventory as the list it has to catch.
  2. Find your thin rows. For each bug in your inventory, count the tests that would fail on it. Every row with one test needs a written decision: accept it, or add a second line that reads something different.
  3. Write the known-good value and a one-line runbook next to every threshold in your nightly lane. Any bar without a known-good value beside it is a guess, and a guess is how checks become flaky.
  4. Audit the mutes. List every check in your current suite that is skipped, muted or set to warn-only. For each, pick one of the three ways out from Part 3, and put a date next to it.
Check yourself

Three questions

Clear all three and session 6 gets stamped in your passport.

1 · Wrenfold's nightly lane runs all eight data checks on the real batch and catches 11 of 12 bugs. Why does it miss train/serve skew?

A lane catches what its tests read. The nightly lane reads data; the skew is in code that the batch does not exercise, so the per-commit lane has to carry it.

2 · A nightly distribution check fails on some nights and passes on others, and nobody can find a bug on the red nights. What is the most likely cause?

A flaky data check is usually a threshold problem, not a code problem. Measure the known-good value, set the bar outside normal variation, and write both down.

3 · With all seventeen tests on, leakage is caught only by d_split and the stale reference table only by d_referential. Why does a second line for them have to be a new test?

Redundancy means a second test that reads a different thing. Running the same reading twice, or more tests that read elsewhere, leaves a thin row thin.
