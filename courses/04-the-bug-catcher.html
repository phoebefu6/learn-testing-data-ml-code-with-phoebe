Part 1 · covers the catch matrix

Reading a catch matrix

5 min live

A catch matrix has one row per bug and one column per test. A cell reads "caught" when that test fails on the output of the pipeline with that bug planted. The verdict for a bug is simple: it ships only if every test in its row passes. The figure is four rows and five columns cut from the full seventeen-column matrix the bench prints below.

LiveWhat "caught" means here, exactly3 min▶

For each bug the bench re-runs the whole pipeline with that one code path changed: load, clean, join, aggregate, fit, serve. Then it runs each enabled test against that run's output, exactly as it runs it against the clean pipeline. A unit test calls the buggy function on its own fake rows. A data check reads the buggy run's real rows. A behaviour test asks the buggy run's model for predictions, and two of them re-run the pipeline again on a changed input: invariance loads the file a second time, directional removes every trip from station 030.

"Caught" is a test failing. Nothing is looked up from a table: if you change a threshold, the test reruns and the cell can change. That is also why the clean row matters. A test that fails on the clean pipeline is not catching anything; it is a false alarm, and the bench counts those separately.

Self-studyHow the bench is built, and what is constructed3 min▶

Real: the trips. HSL publishes Helsinki and Espoo city bike origin-destination data under CC BY 4.0; the data is owned by City Bike Finland. The bench ships every distinct trip departing the five busiest stations of May 2021 (ids 030, 126, 113, 041 and 021), a seeded 50% sample: 13,810 trips. The source file carries every row twice, and the loader keeps that, because it is a fact about the file. The station table is HSL's own, also CC BY 4.0.

Constructed: Wrenfold and its forecast; a capacity-history table with older rows for stations 126 and 113, so the join fan-out has something to fan out on; an old station snapshot lacking every station numbered 300 and up, standing in for a table nobody refreshed. Modelled: the cost units. Everything else, the pipeline, the twelve bugs and the seventeen tests, runs as code. A Python twin of the engine produces the same numbers to the last decimal, and a planted 0.1% fault in one number makes the comparison fail, so the check is known to bite.

Self-studyPlanting bugs is not mutation testing (and where to learn that)1 min▶

Planting a known bug and asking which test fails is the same idea mutation testing automates: generate many small changes to the code and score a suite by how many it kills. That technique, its tools and its scoring are taught in Learn AI QA, session 4. The difference here is the choice of bugs: twelve hand-picked data and ML bug classes rather than mechanical mutations, because the question is which kind of test sees which kind of data bug.

Real world

Three stations nobody listed. HSL's station table has 457 rows. The May 2021 trips mention 432 station ids, and three of them, 754, 997 and 999, are not in the table at all. On a real public dataset, a referential check has something to say on day one: the rule that rejects a trip whose return station is unknown rejects one trip in Wrenfold's sample, which is why the bench allows up to 0.2% and no more.

Part 2 · covers thresholds, false alarms and the two anti-levers

Tighter is not safer

5 min live

Two of the seventeen tests compare this month with a profile stored from a known-good first week: the median trip length and the share of departures in each hour of the day. A distribution check needs a threshold, and the threshold is a choice. Set it loose and real drift slips under it. Set it tight and normal variation, May is not its own first week, trips it on a clean pipeline.

LiveAnti-lever one: "Tighten thresholds"3 min▶

The button moves three bars at once: the median trip length check from 15% to 1%, the hour-profile check from 0.08 to 0.02 and the holdout error bar from 2.2 to 1.9. With all seventeen tests on, the bench still catches 12 of 12 bugs, and now reports 3 false alarms on the clean run. The clean month's median trip is 2.0095 km against the stored week's 1.982, and its forecast error is 1.9113, a little over 1.9. Nothing is wrong with the clean pipeline. The month is just not its first week.

A false alarm costs more than the minute it takes to dismiss. Every one teaches the on-call person that this check is noise, and the next real failure of that check gets dismissed with the same click. Session 6 comes back to this as flaky data tests.

LiveAnti-lever two: "Only unit tests"2 min▶

Turn on the four unit tests and nothing else. They cost 4 units, catch 7 bugs, and let 5 ship: join fan-out, duplicated trips, target leakage, type coercion and the stale reference table. Look at where those five live. Two are in the data itself (the source file's doubled rows, a station table nobody refreshed), one is in a join to a table the fixtures never contain, one is in how the loader reads a column, and one is in which days the model is fitted on. A unit test exercises the function you call on the rows you wrote. None of those five is in a function a fixture calls.

Real world

When a column quietly empties. The Rules of Machine Learning gives, under "Watch for silent failures", the example of a feature column populated in 90% of examples that suddenly drops to 60%. No row is invalid and no type is wrong. Only a check that compares this batch's distribution with a stored one sees it, and only if its threshold sits between normal variation and that drop.

Part 3 · covers the ladder and the cheapest full catch

The cheapest set that catches everything

5 min live

The ladder adds one kind of test at a time and prints three numbers per rung: bugs caught, false alarms, cost per run. Then the bench searches every subset of the seventeen tests, all 131,071 of them, for the cheapest one that catches all twelve bugs with no false alarm.

LiveWhy those six3 min▶
Test (cost)Bugs it covers in the cheapest set
u_distance (1)silent null coercion, km / miles mismatch
u_bucket (1)timezone shift, off-by-one hour
u_parity (1)train/serve skew
d_reconcile (3)join fan-out, duplicated trips, dropped station, label shift, type coercion
d_referential (3)stale reference table (and type coercion again)
d_split (1)target leakage

Three cheap unit tests take the four bugs that live inside small functions, plus the skew. The row reconciliation, counting rows from raw to clean to aggregate with its own independent code, is the single most productive test on the bench: five bugs for 3 units. The other two data checks each own one bug nothing else in the set sees. The set is the only one at 10 units; the next cheapest sets cost 11.

Self-studyThe cheapest set knows the answers3 min▶

The search had something a real team never has: the list of bugs. It found the cheapest cover for these twelve. Next month's bug is a thirteenth, and the set has no slack for it: leakage and the stale table are each caught by exactly one test in it. The seven tests the search dropped are not useless; several are the second line on bugs the set already covers, and the behaviour tests are the only ones that read the model's predictions at all.

So read the result as a floor, not a plan. "Every bug class we know about is caught by at least one cheap test" is the minimum; how much redundancy to buy on top, and where to run it, is the strategy question session 6 answers with a runtime budget.

Real world

Every test the same weight, on purpose. The ML Test Score gives each of its 28 tests the same points, half for running it by hand with the results written down, a full point for running it automatically. The authors say this is intentional, because the relative importance of tests varies by team. The bench takes the opposite route for one pipeline: it measures what each test catches and what it costs, which is only possible once you have named the bugs.

Build-along

Run the ladder on the bench

★ 22 min · everyone builds

The bench below is the real thing (Constructed Wrenfold example, real HSL trips). The first press of a preset takes a second or two: it runs the clean pipeline and all twelve buggy ones, with every test. After that, toggling a test only re-reads the matrix. Every number in the steps is one the widget prints; check each as you go.

Start at "As found". One test, the smoke test, 1 unit. The headline reads 12 of 12 bugs ship. Scan the matrix: the smoke column passes in every row.

Press "+ unit tests". 7 caught, 5 cost units. Read which five still ship and write them down next to your session 1 guesses.

★ Step 2 · the rung, as the bench prints it+ unit tests 7 caught 5 ship 0 false alarms 5 units ships: join fan-out, duplicated trips, target leakage, type coercion, stale reference table

Press "+ schema", then "+ data checks", then "+ behaviour tests". Record the three numbers for each rung. Schema adds type coercion (8 caught, 7 units). The data checks close every row (12 caught, 29 units). The behaviour tests add no catch and 50 more units (12 caught, 79 units).

Press "Tighten thresholds" with all seventeen on. Still 12 caught, now 3 false alarms. Find the three noisy cells in the clean row: d_dist_drift, d_hour_drift and m_holdout. Press it again to go back to normal.

Press "Only unit tests". 4 units, 7 caught, the same five ship. Then press "Cheapest full catch" and read the six tests it switches on: 12 caught, 0 false alarms, 10 units.

★ Step 5 · Wrenfold's test plan, page four (constructed)CHEAPEST FULL CATCH, measured on 12 known bugs, normal thresholds u_distance 1 null coercion, km / miles u_bucket 1 timezone, off-by-one hour u_parity 1 train/serve skew d_reconcile 3 fan-out, duplicates, dropped station, label shift, type coercion d_referential 3 stale reference table d_split 1 target leakage total 10 units per run (all 17 tests: 79)

Score your session 1 inventory. For each of the twelve rows, did your guessed test appear in that bug's row of the matrix? Count your hits. Then turn off one test of the cheapest six at a time and watch which bug starts to ship: that is the single point of failure each test is carrying.

Check the clean row before you trust a column. A test that fails on the clean pipeline marks every bug as caught and means nothing. Before reading any column as coverage, read its clean-row cell.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · With "Tighten thresholds" on, the hour-profile check marks every one of the twelve bugs as caught. Why is that not good coverage?

A test that always fails is a false alarm, not a catch. Read the clean-row cell of a column before you count it as coverage.

2 · The four unit tests catch 7 bugs and let 5 ship. What do the five have in common?

A unit test reads the code it calls on the rows you wrote. The doubled source file and the stale station table are not in your code at all; the data checks read the real rows and see them.

3 · The cheapest full catch is six tests for 10 units, against 79 units for all seventeen. What is the honest way to use that result?

The search optimised for twelve bugs it was given. Leakage and the stale table each hang on one test in the set. Session 6 decides what to add, and when each test runs.

Catch matrixRows are bugs, columns are tests, a cell is caught when the test fails on that bug's output.

Read the clean rowA test that fails with no bug is a false alarm, and it marks every bug caught.
